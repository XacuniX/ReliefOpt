# General Preferences
- Prefers the agent to run tasks autonomously without repeatedly asking for permission — explicitly frustrated when the agent kept pausing for approval ("you kept asking my permission, i want it to be done autonomously"); will pick auto-accept options when available and invokes `cmd --yolo` to force fully autonomous runs with no prompts. Confidence: 0.95
- Prefers to unblock the agent by handling steps the agent struggled with (e.g., installing a dependency like `@huggingface/transformers`) themselves rather than have the agent keep retrying. Confidence: 0.6
- Prefers login/authentication page as the default entry point (e.g., `/` and `*` routes redirect to login, not dashboard). Confidence: 0.8
- Communicates casually and briefly — informal affirmatives ("yea"), minimal explanations, typos are fine. No need for formalities. Confidence: 0.7
- Prefers point-form/bullet-style presentation scripts and documentation — not word-for-word prose. Relaxed grammar is explicitly acceptable in demo scripts. Confidence: 0.85
- Prefers role-based default routing — different user roles should land on different pages after authentication (e.g., field worker → map, admin → dashboard). Confidence: 0.65
- Prefers mobile UI to have feature parity with desktop — key actions like sign-out must be accessible on both form factors. Confidence: 0.6
- Prefers hiding developer/debug overlays (e.g., demo switchers, role toggles) from the user-facing UI when the app is in a demo-ready state. Confidence: 0.6
- Values eye-friendly, comfortable color schemes — light mode should avoid harsh/sterile whites and use softer tones. Confidence: 0.6
- Prefers tables to visually stand out from the page background — alternating row colors (zebra striping) or other differentiation so rows don't blend into the surrounding surface. Confidence: 0.7
- Prefers dark mode palettes that feel professional and industry-relevant — not generic or overly playful. Confidence: 0.6
- Prefers pasted task specs/code to be implemented faithfully as given — exact code, function names, and arguments preserved rather than adapted or "improved" (repeatedly pastes formal specs with exact API signatures to keep, e.g. `makeEntry`/`drainQueue`/`getStatus`). Confidence: 0.9
- Wants completed work verified against the provided checklist before reporting done ("Theres a checklist to follow after ur done to verify your output"); follows up to confirm checklist verification happened ("did you verify it with the R1 Checklist I provided?", "Did it pass R2 Checklist", "Did it pass R3 Checklist") and expects an item-by-item status rather than a blanket "done" (every pasted task spec carries a checklist to verify against). Confidence: 0.97
- Values honest reporting of what could and could not be verified — expects the agent to explicitly separate "code-verified" items from "needs a real browser/mic" items instead of claiming full completion (explicitly asks for tasks to be categorized as completed / must-be-done-manually / still pending). Confidence: 0.9
- Wants the agent to verify task status against the actual codebase and automated checks (file inspection, builds, scripted tests, headless browser or other methods) rather than taking a task list at face value — confirming what is actually implemented and what still needs manual/hardware verification. Confidence: 0.7
- Prefers to receive commit messages as ready-to-paste text rather than having the agent run the git commit itself — wants to control when commits happen ("dont do a commit yourself, just make me the message", "just suggest"). Confidence: 0.85
- Prefers one-line commit messages — a single-line subject with no body, trailers, or extra detail ("one liner commit message"). Confidence: 0.8
- Prefers dialogs/modals to be non-dismissible during in-progress states (recording, transcribing, unsaved/unedited results) — backdrop clicks, Escape, and the close button must not be able to close them and lose work; persistence can lift once the state is safe to abandon. Confidence: 0.8
- Prefers progress/loading percentages displayed as whole numbers only — no decimal points (e.g., `Math.floor(progress)`). Confidence: 0.75
- Prefers user-initiated actions (e.g., audio recording) to run indefinitely until the user stops them, rather than being auto-capped by an arbitrary time limit — explicitly asked to remove a 15-second recording cap that had been added. Confidence: 0.85
- Prefers auto-extracted data (e.g., speech-to-text field extraction) to be user-editable — fields should render as editable controls (dropdowns, number inputs, checkboxes) so the user can click and correct anything the extraction got wrong, rather than presenting read-only results. Confidence: 0.7
- Prefers the agent to proceed without waiting on teammates or unimplemented dependencies — wire against stubs/empty functions (e.g., a teammate's `applyRemoteChange` that is still an empty function) so the feature starts working the moment the dependency lands; the spec explicitly said "that is fine, it will start working the moment they finish. Do not wait for them." Confidence: 0.6
- Prefers project docs/task files (e.g., TASKS.md) to be updated in lockstep with code changes — when a feature/requirement is removed or altered, the spec and checklist must be edited to drop stale references so docs don't contradict the code ("update the task.md accordingly, to remove this bit"). Confidence: 0.8
- Prefers formal, numbered requirement notation and precise domain vocabulary in requirements/architecture documents — numbered IDs (FR-*/NFR-*), explicitly defined terms (Proposal, Outbox, Snapshot, SSoT, `lastCentralSyncTimestamp`), and a formally named consistency model rather than loose prose. Confidence: 0.6
- Prefers design/requirements documents to explain rationale ("why"), not just state requirements — e.g., detailing how a design choice prevents specific failure modes (split-brain, cyclic delta loops, unauthorized disconnected mutation). Confidence: 0.65
- Prefers final deliverables (e.g., SRS) to cite only actual source/config files — not internal dev-reference docs like TASKS.md, Verification.md, or gap-analysis docs, which are dev-only and won't be part of the submission. Confidence: 0.85
- Prefers requirements/SRS documents to be derived from actual codebase inspection with explicit markers distinguishing verified ([IMPLEMENTED]), inferred ([INFERRED]), and planned-but-unbuilt ([PLANNED]) items, and to avoid inventing features that aren't present or scaffolded. Confidence: 0.7
- Prefers a real client-server architecture with a backend server as the single source of truth (SSoT) and backend-owned authentication — login handled by the server, not an in-browser authoritative session. Confidence: 0.8
- Prefers explicit online/offline/reconnect mode semantics: online = stay-connected reads/writes to the backend (like a normal online management system); offline = local cache + outbox with P2P limited to fetching only newer timestamp-gated snapshots (later `lastCentralSyncTimestamp`) and never merging peer proposals; reconnect = push outbox, pull latest snapshot, resume online mode. Confidence: 0.75
- Prefers the agent to first restate its understanding of a requested change and enumerate what it will update before actually applying edits to a document. Confidence: 0.65
- Values proactive critical analysis — asks the agent to surface problems in the current system and implementation risks ("any issue you will run into while implementing it?") rather than only executing to spec; wants honest flagging of model gaps, hard implementation parts, and existing code debt before building. Confidence: 0.6
- Prefers to be consulted on design/architecture decisions one question at a time, kept as short as possible, and to make the final call themselves rather than the agent choosing unilaterally ("ask me each question one by one as short as possible and i will decide on whats best for the system"). Confidence: 0.8
